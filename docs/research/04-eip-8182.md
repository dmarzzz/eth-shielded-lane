# EIP-8182 Private ETH and ERC-20 Transfers: primary-source notes

Last reviewed: 2026-09-17. Author: Tom Lehman. Created 2026-03-03. Status: Review. Proposed for Hegotá 2026-05-25.

## Design

- System contract at `0x...81820`. "There is no proxy, no admin function, and no on-chain upgrade mechanism."
- Notes: `ownerCommitment = poseidon(ownerNullifierKeyHash, noteSecret)`; `noteBodyCommitment = poseidon(ownerCommitment, amount, tokenAddress)`; `noteCommitment = poseidon(noteBodyCommitment, leafIndex)`. "leafIndex is the sequential note-tree leaf index assigned by the contract at insertion time."
- Depth-32 append-only Poseidon2 tree; 500-block root ring; auth-policy registry tree with 64-block root window.
- Groth16 over BN254, 256-byte proof, "a one-time multi-party trusted-setup ceremony." "The proof system is fork-swappable via system contract code replacement."
- Split proof: pool proof plus a permissionless auth proof verified via `staticcall` to a user-registered verifier.
- Deposits are proof-free. Transfers are 2-in / 3-out with slot 2 reserved for an optional private fee note. Withdrawals execute a low-level CALL "with all remaining gas."
- State the contract maintains: tree, root ring, `mapping(uint256 => bool)` nullifier set, intent-replay-ID set, auth registry, user entries.
- "Batching: none; each transact is single ~2-input + 3-output unit."
- Rationale for UTXO over accounts: "Account-based encrypted balances reveal access patterns."

## Magicians thread (27889)

- middlemarch, 2026-04-27: "Each transact adds 3 unbounded state entries: 2 nullifier slots, 1 intent-replay-ID slot... 192 bytes of new state" per transaction; about 700 MB per year at 10,000 daily transfers.
- middlemarch, 2026-05-26: "the unavoidable issue is still unprunable nullifier-type data."
- JohnG, 2026-04-24: "Regarding scalability, have you thought about proof aggregation?" No substantive reply visible.
- The draft was rewritten to make recursive auth the v0 architecture, to avoid a hard fork per auth method and to avoid splitting the anonymity set.
- No FOCIL, inclusion-list, or block-segment discussion in the thread.

## What we take from it

- Pool semantics, note structure, fee-note pattern, split auth (ADR-0001).
- The permanent nullifier mapping is the thing the lane replaces (v0: spent bits; v2: window).
- leafIndex-in-commitment forces the deposit-ordering rule (ADR-0003, OQ-5).
- The inline CALL withdrawal is not lane-safe (ADR-0004, OQ-7).
