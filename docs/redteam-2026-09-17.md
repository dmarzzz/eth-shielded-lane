# Red team: six hostile readings of the shielded lane

Date: 2026-09-17. Target: README, `docs/design/spec-draft.md`, ADR-0002 through ADR-0008, and the 16-tweet thread in `~/x-poster/shielded-lane-thread.txt`.

Method: each section is written in the voice and priorities of a person whose work this design borrows from, grounded in what that person actually published (per `docs/research/`). Objections are ordered strongest first. Severity is one of: **fatal** (the design as written does not work and the claim must be withdrawn), **serious** (works only after a real redesign of a named component), **fixable** (a spec gap, not a design error).

Tweet numbering: tweets are numbered 1 to 16 in file order, counting `---` separators. Tweet 1 is the hero, tweet 16 is the link dump.

---

## 1. Sean Bowe (Zcash, Tachyon)

> "Validators must only maintain the leading edge of revealed nullifiers ... but can otherwise permanently prune the nullifiers and everything else about the Tachyon transaction history." (forum, 2025-11-04)

### B1. "v2 is a state-model swap, not a redesign" is false, and the rollout order in my own post says why

**Severity: fatal (to the claim), serious (to the design).**

ADR-0005 Consequences says "The lane's state and interface are designed so v2 is a state-model swap, not a redesign." The rollout order I published is: out-of-band payments, then aggregation via PCD, then the nullifier derivation change, then a new accumulator, then removal of in-band secret distribution, then wallet PCD state. Your v0 inherits EIP-8182's note structure (`noteCommitment = poseidon(noteBodyCommitment, leafIndex)`), in-band note data (spec Section 5, `emit LaneOutput(op.out_note_data)`), and therefore trial decryption, which is the thing Tachyon exists to remove because "this simply does not scale." Getting to your spec Section 10 means changing the commitment, the nullifier derivation, the accumulator, and the payment protocol, which is every layer of the pool except the word "shielded."

*What would answer it:* state v0 and v2 as two different pools with a migration, publish the v2 note format, and drop the "swap" framing from ADR-0005 and from tweet 6.

### B2. There is no "simple non-recursive aggregation" tier, and Groth16 does not fold

**Severity: fatal to the tier ladder.**

ADR-0005 defines v1 as "one aggregate per committee member (16), non-recursive" and the README tier table repeats it. For proofs of *different statements* there are exactly three known options: batch verification (which does not reduce bandwidth, you still gossip 256 bytes per transaction, so it is not aggregation), a SNARK that verifies n SNARKs (recursive, and inside a Groth16 circuit a BN254 pairing check is brutally expensive), or folding, which is what Ragu does and which Groth16 structurally cannot do. Tachyon's aggregation property, "block producers can aggregate shielded transactions without user coordination," is a property of the folding scheme, not of the block structure; you cannot get it by choosing a committee. v1 as written is a name for a thing that does not exist.

*What would answer it:* delete v1, or define it precisely as "16 recursive Groth16 wraps" and publish the circuit size and proving time for one wrap over ~64 inner proofs.

### B3. You justify BN254 with an EVM constraint that your own design removes

**Severity: serious.**

ADR-0005 Context and tweet 14 both argue from "the EVM only has BN254 pairing precompiles," and OQ-1 concludes that a Groth16-wrapped bn254/grumpkin PCD "looks like the only route that skips a new precompile." But spec Section 4 verifies the lane *natively in the client*, not in the EVM. Once verification is native, the precompile set is irrelevant, and the field opens to exactly the hash-based options Pierre argued for (`docs/research/05`), which are post-quantum, need no trusted setup, and fold. Meanwhile grumpkin has no pairing, so the "Groth16 wrap" you sketch means proving an IPA verifier over a non-native field, which is the single most expensive thing in this whole space and the reason Ragu lives on Pasta with no wrap at all.

*What would answer it:* rewrite ADR-0005 Context to say the constraint is "CL clients must link a verifier," then re-run the candidate comparison, at which point BN254 Groth16 stops being the obvious v0.

### B4 (bonus, free). Oblivious sync is not a footnote

OQ-8 is marked `open` while tweet 6 asserts "users carry the proof their old ones are clean" as a settled property. The reason an untrusted service can extend your PCD is that "nullifiers need to be changed so that they are not determined by the note commitment but rather the other way around," and that the protocol "forces them to periodically evolve in an unlinkable way." Without the derivation inversion, the service learns the nullifiers, and the privacy claim inverts. **Severity: serious.** *Answer:* move the derivation inversion out of spec Section 10's bullet list and into a normative v2 section before any public post repeats the tweet-6 claim.

## 2. Toni Wahrstätter (nero_eth): Native UTXOs author, EIP-7805 co-author

> "Keep in state only the minimal fact the next transaction's validity depends on, usually just 'has this been used?', and push existence and contents into append-only history you prove against on demand."

### T1. Your nullifier bitfield is a category error, so v0's headline state number is wrong

**Severity: fatal.**

Spec Section 2 declares `nullifier_state: v0: bitfield keyed by nullifier index`, and the README proof-tier table prices it at "~0.3 B/tx, Nero spent-bit style." My bitfield works because a UTXO has "a protocol-assigned monotonic index"; the protocol hands out index 0, 1, 2, and a dense bitfield is the natural encoding. A nullifier is a user-derived pseudorandom 256-bit field element. There is no index. You cannot key a dense bitfield on an unpredictable sparse set, and if you tried to assign indices at reveal time you would have to store the nullifier to map it, which is exactly the mapping in EIP-8182 you say you are replacing. v0's real state cost is 8182's cost, and the tier table advertises a 100x saving that does not exist.

*What would answer it:* replace the table row with the honest figure (a set entry per nullifier, roughly 32 to 64 bytes) and say plainly that v0 buys inclusion and independence, not state.

### T2. You imported my chassis, dropped the one invariant it needs, and then added two more rings that need it

**Severity: serious.**

CPerezz's note on my thread is the load-bearing one: "the spec needs the invariant that `batches[b]` is readable in state no later than the first overwrite of an era-b ring slot," because EIP-4444 deletes the bodies the openings live in. Your spec Section 2 copies `openings_root_ring[8192]` and `sealed_batches` and writes "sealing invariant TBD (OQ-9)." You then add `commitment_root_ring[8192]` with the same retention problem, and v2 adds per-block nullifier set roots that users must prove non-membership against for arbitrarily old blocks. OQ-9 is not one open question carried over; it is three, and the third one is worse because it is load-bearing for spending, not just for auditing.

*What would answer it:* write the sealing schedule as a normative section covering all three structures before claiming the pruning property anywhere.

### T3. "Enforcement is just FOCIL" is not true, and the 8 KiB budget makes the lane's censorship resistance a rounding error

**Severity: serious.**

`MAX_BYTES_PER_INCLUSION_LIST = 8 KiB`, and that budget exists to rescue ordinary censored transactions, which is the entire motivation ("two of the top three builders are actively filtering out transactions interacting with sanctioned addresses"). A lane transfer carries a 256-byte Groth16 proof, two nullifiers, three commitments, a fee, and three note-data blobs; call it 1 to 2 KB. So a committee member can list four to eight lane operations, and only by listing nothing else. ADR-0007 sees this and says "within the 8 KiB limit, **or a lane-specific list**," which is a second IL type, a second gossip topic, a second byte budget, and a change to the attester validity function. That is an amendment to EIP-7805, not a reuse of it, and tweet 8 should not say "enforcement is just FOCIL."

*What would answer it:* specify the lane IL as its own EIP-7805 amendment with its own size and rate limits, and say so in the thread.

### T4 (bonus). Reorgs and unspendable UTXOs

OQ-13 is `open` while tweet 7 states the unshield path as settled. A reorg of block N re-indexes lane outputs and `next_utxo_index`, killing every downstream witness and the specific UTXO a frame transaction at N+1 was built to spend; the one-block unshield gap is precisely the reorg window. Separately, leekt216's point applies unchanged: an unshield to a contract address with no key produces a UTXO nobody can spend, and ADR-0004 has no recipient check, so the lane can irrecoverably burn user value. **Severity: serious.** *Answer:* add a normative reorg rule (anchor to a finalized ring slot, or make openings index-independent) and a recipient-form restriction in ADR-0004.

### T5 (bonus). I declined ZK on this chassis on purpose

I said on the thread that ZK verification "would increase surface area, problems and complexity." Tweet 7 credits me for the part you kept and does not mention that the author of the chassis argued against this exact use of it. **Severity: fixable.** *Answer:* cite the decline in ADR-0004 Context and in the thread.

## 3. Tom Lehman (EIP-8182)

### L1. Drop-on-conflict reshuffles leaf indices, which is the bug ADR-0003 was written to prevent

**Severity: fatal.**

ADR-0003 exists because "EIP-8182 binds `leafIndex` into the note commitment, so lane output indices would depend on how many deposits the builder included," and the fix is to queue deposits. Then spec Section 5 `apply_lane` does `continue` on a nullifier conflict, skipping that op's inserts, which shifts `next_leaf_index` for every op after it in the same lane. You removed the builder's ability to move your indices and handed it to any lane participant who can get a conflicting nullifier listed first. README Section 2's "dropping a conflicting entry needs no re-proof" is only true if nothing downstream is bound to position, and in my design everything is.

*What would answer it:* either drop `leafIndex` from the commitment (ADR-0003 lists this alternative and does not take it) or make dropped ops reserve their index slots so the prefix is stable.

### L2. Killing inline transact kills the reason people use a pool, and you priced the loss at zero

**Severity: serious.**

ADR-0008 drops inline mode and spec Section 9 records "shielded to public, atomic with EVM action: not supported." In 8182 a withdrawal executes a low-level CALL with all remaining gas, which is what makes unshield-act-reshield one transaction: pay a contract, do a swap, land back in the pool with no public intermediate. Your replacement publishes a `(recipient, value)` opening at block N, in the clear, and lets the recipient act at N+1. You have not removed the MEV, you have given searchers one full block of advance notice of a public value transfer, with the recipient address attached. For a privacy system that is a downgrade, not a simplification.

*What would answer it:* quantify what fraction of 8182-style usage is transfer-only versus act-on-exit, and if act-on-exit matters, reopen OQ-7 with a two-block-old anchor for inline spends, which ADR-0008 lists and rejects for "little gain."

### L3. You inherited my trusted setup and promoted it into consensus

**Severity: serious.**

8182 has "a one-time multi-party trusted-setup ceremony" and, critically, "the proof system is fork-swappable via system contract code replacement," which is a contained blast radius: a compromised setup is a bug in one system contract. Your design verifies the same Groth16 in the client at attestation time (spec Section 4, tweet 10), which makes the ceremony's toxic waste a consensus-level assumption and the verifier a client binary, not swappable contract code. Nothing in the repo mentions the ceremony, its coordination, or what "fork-swappable" means once a CL client links the verifying key.

*What would answer it:* an ADR on the ceremony and the verifier-upgrade path under CL verification, plus a note in ADR-0005 that Groth16 in consensus loses 8182's swap property.

### L4 (bonus). "8182 v2" versus hijack

OQ-14 asks whether this is pitched as "8182 v2, a new EIP, or a research post first," and ADR-0001 says the base is 8182 "whose author concedes the state-growth gap this design fills." It is fair to say 8182 has a state-growth problem and unfair to name your thing 8182 v2 without me: you took the note format and the fee note, dropped the withdrawal semantics, dropped inline transact, changed the state model, and moved verification into the consensus layer. That is a different EIP that cites 8182. **Severity: fixable.** *Answer:* answer OQ-14 as "new EIP, cites 8182," and drop the v2 framing. Also verify that `middlemarch` on magicians thread 27889 is the EIP author before tweet 11 attributes that quote "from the author"; `docs/research/04` records the handle and the quote but never records the identity.

## 4. The FOCIL authors (Thiery, Monnot, D'Amato)

> "The Valid function verifies if the execution payload satisfies IL validity conditions either when all transactions are present or when any missing transactions are found to be invalid when appended to the end of the payload."

### F1. You turned "valid if appended" into "verify a SNARK," which is an unpriced DoS on the attestation deadline

**Severity: fatal.**

The reason the conditional rule is cheap is that deciding a missing transaction is invalid costs a nonce check, a balance check, and a gas check. ADR-0007 redefines validity as "anchor in ring, nullifiers not in window, **proof verifies**," so every attester must run pairing checks on every listed-but-omitted lane op before it can decide whether to reject a block. The IL topic is permissionless gossip within the committee and there is no cost to listing an op with a garbage proof, so one member, or anyone who can get bytes onto that topic, can force the whole attesting set to burn its t=0 to t=3 budget on failing verifications. FOCIL's validity rule was designed to be evaluable without execution; you made it require cryptography.

*What would answer it:* make lane-op IL entries carry a bond, or define lane validity for IL purposes as the proof-free predicate (anchor plus nullifier freshness) and accept that a valid-looking op with a bad proof can be omitted.

### F2. "Lane proposer" is a new role with no selection rule, no penalty, and two seconds to prove

**Severity: fatal.**

ADR-0008 lays out the schedule: committee works t=0 to t=8, views freeze at t=9, and "the lane proposer must hand the lane to the proposer by t=11." Tweet 9 draws it as a swimlane and tweet 4 says the lane is "built by the FOCIL committee," which is a third answer. At v1 or v2 that role must produce a recursive aggregate over the whole lane inside a two-second window, and OQ-1 concedes "nobody's benchmarked it." There is no selection rule, no slashing condition, no payment (OQ-3 is `researching`), and no spec text; spec Section 6 literally reads `shielded_lane_proposer: TBD`. Ethereum does not add unpaid, unslashed, latency-critical roles to the critical path.

*What would answer it:* a proving-time budget with measured numbers for the chosen system, and a role definition with selection, payment, and an equivocation penalty, before anything is posted.

### F3. Withholding the lane body breaks the t=3 check, and the rebuild story does not survive v2

**Severity: serious.**

The proposer commits `shielded_lane_root` at t=0 (spec Section 6) and attesters must verify the lane by t=3 (tweet 9, ADR-0008). If the body is not published, attesters can neither verify nor evaluate the IL condition, so they either reject (a cheap griefing vector against every proposer) or accept (which makes the commitment meaningless). ADR-0007 answers "a withheld lane is rebuildable by anyone with the transactions," which is true at v0 where every proof travels with its op, and false at v2 where rebuilding means re-running the aggregate, which by F2's own admission does not fit in a slot. This is FOCIL's data-availability boundary being crossed by a new artifact that has no PTC-style attestation of its own.

*What would answer it:* an availability rule for the lane body (its own PTC-style vote, or a rule that the lane commitment is only binding once the body is seen), specified in ADR-0007.

### F4 (bonus). The block-full loophole did not close, it moved

ADR-0006 claims a separate lane gas budget "closes the FOCIL 'block full' loophole." A lane with `LANE_GAS_LIMIT` can be full too, and whoever assembles the lane chooses which listed ops fill it. You have replaced "the builder can claim the block is full" with "the lane proposer can claim the lane is full," and the lane proposer is the unaccountable role from F2. **Severity: serious.** *Answer:* either size the lane so it is never binding against the committee's output, or specify a priority rule that makes listed ops strictly preempt unlisted ones.

### F5 (bonus). The composed timeline is invented

ADR-0008 and tweet 9 mix FOCIL's t=8/9/11 (a Hegotá EIP) with ePBS t=0/3/6 (a Glamsterdam EIP) as if the composition is settled. EIP-7805's own attestation deadline in `docs/research/03` is slot N+1 **t=4s**, not t=3. Neither EIP specifies the other's timings, both are under active slot-restructuring pressure, and the design's central "they are built in parallel" claim rests entirely on those numbers. **Severity: fixable.** *Answer:* label the timeline as an assumed composition and cite where each number comes from.

## 5. Max Resnick (MCP, BRAID) and Mike Neuder (ePBS)

### R1. The dashed line hides two shared writes, both of them in your own spec

**Severity: serious.**

Tweet 4 says "neither lane ever reads the other's state" and ADR-0004 says "the lane writes zero account state." Spec Section 5 says `burn(S.vault, base_fee_lane); credit_tip(lane.proposer, op.fee - base_fee_lane)`. `credit_tip` is an account balance write, performed inside the lane, to an account the payload can also touch. `S.vault` is a balance that payload deposits credit and lane fees debit in the same block. Under EIP-7928 those are declared write conflicts and BALs will say so out loud, which is awkward given the README lists 7928 as the thing that proves the access sets are disjoint. The defensible claim is narrower: the lane's *validity* does not depend on the payload. Commutativity of the state transition is a different and stronger claim and it is currently false as written.

*What would answer it:* pay lane tips inside the lane (a shielded note or a transparent UTXO to the lane proposer) and state the vault as a jointly-written but additively-safe account with an explicit argument.

### R2. "Who pays when they conflict" is the exact question from the concurrent-block-proposers thread, and you answered it by assuming it away

**Severity: serious.**

fradamt asked on ethresear.ch 18777, "who pays if the transactions of the second payload are invalidated by the first one?" and `docs/research/06` records it as unanswered. Your answer is that the lanes never conflict, but spec Section 5 drops conflicting lane ops, and a dropped op pays no fee (the `continue` skips the fee line) while its proof, its nullifiers, and its note data were already gossiped, verified in the batch at Section 4, and committed to. That is free data availability plus free verification, paid for by every node, charged to nobody. It is the same failure mode the MCP literature flags, relocated from cross-bundle invalidation to intra-lane conflict, and your own note says the duplication-penalizing TFM is the transferable result.

*What would answer it:* charge dropped ops (verification and DA are consumed either way), or make conflicting ops a lane-validity failure rather than a silent drop.

### R3. Builder revenue now depends on a committee artifact the builder does not control

**Severity: serious.**

Under ePBS the whole point is that the payload's fate stops depending on the proposer's honesty: the proposer commits to a bid at t=0, the PTC votes on payload presence, and the builder's payment is not hostage to proposer behavior. Here the same beacon block carries `shielded_lane_root`, and if the lane is invalid, unavailable, or omits a listed op, the block dies and the builder's bid dies with it. Builders will price that as risk, which means the lane is a tax on the payload that nobody in the lane pays. ADR-0008's "if the builder withholds payload N+1, the lane still applies" is the easy direction; the hard direction is not addressed anywhere.

*What would answer it:* specify what happens to the builder's payment and the PTC vote when the lane fails validation, and show that lane failure cannot be induced by a third party.

### R4 (bonus). "This does the opposite" and "builders are specialized in contention"

Tweet 12 says every MCP design merges into one execution and "this does the opposite," and tweet 13 says private transfers are "not contentious." Neither lands. BRAID's premise is already that lanes over disjoint state do not need merging; the hard and interesting part is the contended part, so a design that handles only the disjoint part has not done MCP, it has built a second blob-like lane with its own fee market. And private transfers are not uncontended: two racing spends of the same note contend for the nullifier, the anonymity set itself is a shared resource, and your unshield publishes a public `(recipient, value)` one block before the recipient can act, which is a front-runnable signal that did not exist in the inline design. **Severity: fixable (framing), serious (the unshield signal).** *Answer:* rewrite tweet 12 as "this composes at the beacon-block level instead of merging at the execution level," and address the one-block unshield signal in ADR-0004 Consequences.

### R5 (bonus). The FOCIL-is-MCP quote is a commenter, not the authors

Tweet 12 says "FOCIL's own thread calls it 'MCP with single-tx mini-blocks'." `docs/research/03` attributes that to **The-CTra1n, reply #6**, and the actual words are "is a generalization/extension of the concurrent block proposer idea" and "Each IL 'proposer' ... is proposing m mini-blocks=single transactions." The quoted phrase is a paraphrase attributed to the wrong party. **Severity: fixable.** *Answer:* quote it as a thread commenter, verbatim, or cut it.

## 6. A skeptical core dev (client implementer)

### C1. This puts BN254 pairing verification and a trusted setup inside the consensus layer, on the attestation critical path

**Severity: fatal as scoped.**

Spec Section 4 has attesters running `batch_verify_groth16` by t=3 (tweet 9, tweet 10). Consensus clients today link BLS12-381 for signatures; they do not link BN254, they do not carry Groth16 verifiers, and they do not embed circuit-specific verifying keys from a ceremony. So this is a new curve, a new proof system, a ceremony artifact shipped in client binaries, and a new failure mode where a verifier bug is a consensus split rather than a contract bug. Batch verification of proofs over different public inputs still costs one multi-scalar multiplication per proof for the public-input commitment plus randomization, so at a few hundred to a thousand ops per block you are adding a real, variable, adversary-controlled chunk of a three-second window that already has to do attestation, IL checking, and fork choice. There is no number for this anywhere; OQ-6 is `not started`.

*What would answer it:* a measured benchmark of batched BN254 Groth16 at the target op count on the slowest supported hardware, as a fraction of the t=0 to t=3 budget, before any other work.

### C2. The CL/EL split is undrawn and the pieces land on both sides of the engine API

**Severity: serious.**

`shielded_lane_root` is a beacon block field (spec Section 6) and attesters validate the lane at t=3, so validity is consensus-layer. But `apply_lane` writes a commitment tree, a vault balance, a UTXO openings ring, and a deposit queue (spec Section 5), and it runs "after payload," so state is execution-layer, sealed by a block-end system operation in the style of EIP-7002. That means a new engine API surface, a state transition the CL commits to before the EL has run, and a root the CL attested to at t=3 that the EL only produces at execution. EIP-7732 is already rewriting exactly this boundary. Nobody in the repo has said which client owns `apply_lane`.

*What would answer it:* an ADR that draws the CL/EL split explicitly, names the engine API changes, and says which side holds the verifier.

### C3. This is not one fork of work, and it depends on five unshipped things at once

**Severity: serious.**

The dependency table in README Section 6 needs EIP-7805 (Hegotá, only confirmed EIP), EIP-7732 and EIP-7928 (Glamsterdam headliners, devnets), EIP-8141 (CFI, not scheduled), and EIP-8182 (PFI, Review). The lane itself adds: a beacon block field, a lane validity function, a new gossip topic, a second inclusion-list type, a lane fee market with its own EIP-1559 controller, a system contract, three ring structures with a sealing schedule, a queue drained at block end, a new CL-side proof system, and a role that does not exist. Any one of those is a fork's worth of contention; the combination is three or four, and the first dependency to slip takes the design with it.

*What would answer it:* define the minimum viable version that depends on FOCIL alone (no ePBS timing claims, no frames, no BALs), and stage the rest.

### C4 (bonus). The one-block latency claims are off by one

Spec Section 9 says a lane unshield is "spendable at N+1" and a deposit is "spendable at N+1." Work it through: the lane for block N+1 is assembled during slot N, but the commitment root as of end of block N is not final until payload N is revealed at t=6 of slot N and the deposit queue drains at block end. A note created by block N's lane therefore cannot be anchored by a lane op that was built before that root existed, so real shielded-to-shielded latency is two blocks, not one. Meanwhile spec Section 4's `lane_valid` says "S = shielded view of state as of end of block N-1" while ADR-0003 says the anchor is "end of block N-1 **or older**," and the two do not say the same thing about which block's lane is being validated. **Severity: fixable.** *Answer:* write the latency table from the timeline rather than from intent, and fix the off-by-one in Section 4.

### C5 (bonus). Groth16 malleability versus a lane commitment

Groth16 proofs are re-randomizable, so the same logical lane can be encoded as many distinct byte strings with different `shielded_lane_root` values. Any rule that says "a withheld lane is rebuildable by anyone with the transactions" (ADR-0007) needs a canonical encoding, or two honest rebuilders disagree on the root. **Severity: fixable.** *Answer:* define a canonical serialization and commit to the op set, not the proof bytes.

## Ranked top 5, across all personas

1. **The v0 nullifier bitfield cannot exist (T1, fatal).** `nullifier_state: bitfield keyed by nullifier index` (spec Section 2) and "~0.3 B/tx, Nero spent-bit style" (README tier table) apply an indexed-UTXO encoding to unindexed 256-bit values. v0's state saving is zero; v0 is EIP-8182's state model with a different block placement. Fix the table before anyone reads it.
2. **Drop-on-conflict is incompatible with both aggregation and `leafIndex` (B2, L1, fatal).** README Section 2 says dropping a conflicting op "needs no re-proof." At v2 a single aggregate over the op set is invalidated by any drop; at v0 with 8182 commitments, a drop shifts `next_leaf_index` for every later op, which is the exact nondeterminism ADR-0003 was written to eliminate. The commutativity story does not survive its own conflict rule.
3. **"Valid if appended" now requires attesters to verify SNARKs, with no cost to the lister (F1, fatal).** ADR-0007 makes lane-op validity include proof verification, so any committee member can force every attester to run pairings on garbage in the t=0 to t=3 window. FOCIL's rule was cheap on purpose; this makes the censorship-resistance mechanism the DoS vector.
4. **The lane proposer is an undefined role with a two-second proving window (F2, fatal).** Spec Section 6 says `shielded_lane_proposer: TBD`; ADR-0008 gives the role t=9 to t=11 to produce an aggregate; OQ-1 says nobody has benchmarked it; OQ-3 says payment and equivocation are open.
